#  MAC 함수 부동소수점 정밀도 분석 보고서

##  개요

MAC(Multiply-Accumulate) 연산 결과가 **다른 사람의 코드와 미세하게 다른 값**으로 나오는 현상을 발견하고, 그 원인을 추적한 과정을 정리한 문서입니다.

결론부터 말하면 — **코드 버그가 아니라 부동소수점 연산의 근본적 특성** 때문이었습니다.

---

##  문제 상황

### 증상

특정 테스트 케이스(`size_13_2`, `size_25_1`)에서 Cross 점수와 X 점수가 **완전히 같은 값**으로 나와 판정이 `UNDECIDED`로 처리되는 문제 발생.

### 3단계: 부동소수점의 결합법칙 미성립 가설

부동소수점 덧셈은 **결합법칙이 성립하지 않는다**는 특성을 상기.

```python
>>> (0.1 + 0.2) + 0.3
0.6000000000000001
>>> 0.1 + (0.2 + 0.3)
0.6
```

→ **더하는 순서가 다르면 결과값의 마지막 몇 비트가 달라질 수 있음**.

##  2. 원인 분석: 기존 방식 1은 왜 완전히 같게 나와서 실패했을까?

### (1) Python 파이프라인의 차이: Generator Expression + `sum()` vs 명시적 Loop 누적

가장 결정적인 차이는 방식 1(기존)과 방식 C(이중 for문 행 우선)의 비교에서 드러납니다.
둘 다 접근 방향은 '행 우선(Row-major)'으로 같지만, 연산 결과는 달랐습니다.

* **기존 방식 1 (`sum(...)` + 제너레이터):**
- Python 내부의 `sum()` C 구현체는 제너레이터 표현식(`for r ... for c ...`)을 순회하며 바이트코드 수준에서 내부 임시 변수 및 내부 C 루프 누적을 진행합니다.<br> 

- 이 때 **Cross 패턴과 X 패턴의 비대칭적 데이터 구조에도 불구하고, 곱셈과 누적 과정에서 발생하는 비트 절삭 타이밍이 완벽하게 대칭을 이뤄 비트 단위까지 100% 일치하는 값**으로 수렴해 버린 것입니다.

* **방식 C (명시적 `total_sum += ...`):**
Python 루프 레벨에서 `total_sum`이라는 객체에 원소별 연산 결과를 순차적으로 덧셈 연산합니다. 이 과정에서 발생한 부동소수점 누적 오차(ULP, Unit in the Last Place)가 Cross와 X 사이에 아주 미세하게(예: $0.900...02$ vs $0.899...91$) 다르게 형성되었습니다.

### (2) 부동소수점 덧셈의 결합법칙 미성립

부동소수점 덧셈은 $(a + b) + c \neq a + (b + c)$ 특성을 가집니다.

* **Cross 패턴**과 **X 패턴**은 대각선/십자가 형태의 유효 데이터 배치가 다릅니다.

* 연산 순서(행 우선 vs 열 우선)나 누적 방식(제너레이터 vs 단일 변수 누적 vs row_sum)이 달라지면 **가수부(52비트)를 넘어가는 하위 비트가 버려지는 타이밍과 위치**가 달라진다!

##  3. 방식별 상세 분석

### (1) 방식 1 (기존: 제너레이터 + `sum()`)

```python
s1 = sum(self.data[r][c] * pathern.data[r][c] 
for r in range(n) 
for c in range(n))

```

* **문제점:** Python `sum()` 함수 내부에서 제너레이터를 소진하며 덧셈을 수행할 때, 테스트 케이스의 대칭적 특성과 맞아떨어지면서 Cross와 X 점수가 **소수점 17자리 비트까지 완벽히 동일한 수치($0.9, 7.5, 4.9$)로 보정/절삭**되었습니다.
 => 즉, 소수점 자리를 늘려도 100%일치한다! 왜냐하면 비트 수준에서 가수부 비트(52번째 비트)까지 100% 일치하기 때문!
* **결과:** 판정 로직이 동점(`UNDECIDED`)으로 간주하여 `FAIL` 발생.

### (2) 방식 A (열 우선 순회)

```python
for c in range(self.n):
    for r in range(self.n):
        total_sum += self.data[r][c] * pathern.data[r][c]

```

* **특징:** 행과 열의 순서를 바꿈으로써 데이터 누적 순서를 완전히 뒤엎었습니다.
* **결과:** 오차가 크게 벌어지며 동점이 해소되었습니다. 

### (3) 방식 B (행별 부분합) 및 방식 C (이중 for 명시적 누적)

```python
# 방식 C: 명시적 이중 for문 누적
total_sum = 0
for r in range(self.n):
    for c in range(self.n):
        total_sum += self.data[r][c] * pathern.data[r][c]

```

* **특징:** 제너레이터를 거치지 않고 명시적으로 단일 변수에 연산 결과를 순차 누적했습니다.
* **결과:** 아주 미세한 ULP 단위 오차($10^{-16}$ 수준)가 Cross와 X 사이에 다르게 누적되어, **완전 동점 상태를 벗어나 정상적으로 비교가 가능**해졌습니다.

##  4. 최종 결론 및 시사점

1. **기존 방식 1이 안 됐던 이유:**
`sum()`과 제너레이터 조합의 내부 연산 절삭 타이밍이 Cross/X 패턴의 대칭성과 결합되어 **비트 단위 완전 동점**을 유발
2. **해결책:**
MAC 함수 작성 시 단순히 `sum(generator)` 형태를 사용하는 대신, 명시적 루프 누적(방식 C) 또는 연산 순서 변경(방식 A/B)을 적용하여 부동소수점 누적 오차가 미세하게 반영되도록 수정.
3. **핵심 배운 점:**
부동소수점 연산에서는 "어떤 파이프라인과 순서로 더하느냐"에 따라 동일 수식도 결과 비트가 달라질 수 있다는 점을 실전 데이터로 확인했습니다.

##  배운 점

### 1. 부동소수점의 함정
- **결합법칙 미성립**: `(a+b)+c ≠ a+(b+c)`
- 같은 수식이라도 **계산 순서에 따라 결과가 다름**
- 이는 IEEE 754 표준의 근본적 특성 (버그 아님)

### 2. 디버깅 도구로서의 `float.hex()`
- 육안으로 같아 보이는 값도 비트 단위 비교 가능
- `0.1 + 0.2 == 0.3` 같은 문제를 정확히 진단
- 부동소수점 연산에서 `==` 은 조심할 필요성 있음 

### 3. 다른 사람과 결과가 다를 때
- **먼저 의심할 것**: 계산 순서, 알고리즘 구조
- **버그가 아닐 가능성**이 높음
- 이론값이 아닌 **실제 부동소수점 값**을 비교해야 함

---

##  결론

-  **MAC 함수 코드는 정상**이었음
-  동점 현상의 원인은 **부동소수점 결합법칙 미성립**
-  **순회 순서 변경**(행 우선 → 열 우선)으로 해결
-  다른 사람과 다른 값이 나왔던 것도 **동일한 원인**

>  부동소수점 연산에서 "정확한 값"이란 존재하지 않는다.
> 다만 "충분히 가까운 값"이 존재할 뿐이다.
