
# MinNPU: MiniNPU 시뮬레이터 개발 및 성능 분석 리포트

외부 라이브러리(NumPy, Pandas 등) 사용 없이 파이썬 표준 라이브러리만을 활용하여 구축한 **MiniNPU 시뮬레이터**입니다.  
**$N \times N$** 크기의 패턴과 필터 간 Multiply-Accumulate(MAC) 연산을 수행하고, 패턴 분류 및 연산 성능을 측정·분석합니다.

## 2. 구현 요약

### (1) 라벨 정규화 (Standardization)

`data.json` 또는 사용자 입력 라벨의 다양성(`'+'`, `'cross'`, `'x'`, `'X'`)에 구애받지 않도록, 내부 전처리 함수 `only_normal()`을 통해 표준 라벨(`Cross`, `X`)로 일괄 변환하여 데이터 처리 및 검증의 안정성을 확보했습니다.

### (2) MAC (Multiply-Accumulate) 연산 구현

이중 `for`문 순회 방식으로 직접 구현하였습니다.

$$Score = \sum_{r=0}^{N-1} \sum_{c=0}^{N-1} (Pattern[r][c] \times Filter[r][c])$$

측정 정확도를 높이기 위해 $I/O$ 구간을 제외하고 순수 MAC 연산 구간만을 10회 반복 측정하여 평균 시간(ms)을 산출합니다.

### (3) 부동소수점 비교 및 동점 처리 정책 (Epsilon Policy)

부동소수점 연산 오차로 인한 오판을 방지하기 위해 허용 오차 상수 $\epsilon = 10^{-9}$ 기준을 적용했습니다.

* $\vert{}Score_{Cross} - Score_{X}\vert{} < 10^{-9}$ 인 경우: 동점으로 간주하여 **`UNDECIDED`** 처리
* $Score_{Cross} > Score_{X}$ 인 경우: **`Cross`** 판정
* $Score_{Cross} < Score_{X}$ 인 경우: **`X`** 판정

* **총 테스트 케이스:** 6개
* **통과 (PASS):** 3개 (`size_5_2`, `size_13_1`, `size_25_2`)

---

### (2) FAIL 케이스 원인 분석 (데이터/수치 비교 문제)

총 6개의 테스트 케이스 중 3개 케이스에서 `FAIL`이 발생하였으며, 상세 원인은 다음과 같습니다:

* **실패 케이스 목록:** `size_5_1`, `size_13_2`, `size_25_1`
* **주요 원인 (동점 발생으로 인한 `UNDECIDED` 판정):**
* `size_5_1`: Cross 점수 `0.9` vs X 점수 `0.9` ($\vert A - B \vert = 0.0$)
* `size_13_2`: Cross 점수 `7.5` vs X 점수 `7.5` ($\vert A - B \vert = 0.0$)
* `size_25_1`: Cross 점수 `4.9` vs X 점수 `4.9` ($\vert A - B \vert = 0.0$)


* **진단 결과:**
* 해당 패턴들은 입력 데이터가 Cross 필터와 X 필터 모두에 동일한 유사도를 보이는 대칭 구조를 가지고 있어 MAC 연산 결과가 완벽히 동일했습니다.
* 프로그램 내부의 허용오차 비교 정책($\vert{}Score_{Cross} - Score_{X}\vert{} < 10^{-9}$)에 따라 오판을 방지하고 `UNDECIDED`로 안전하게 판정하였으나, `expected` 값(`Cross` 또는 `X`)과 불일치하여 `FAIL` 처리되었습니다.
* 이는 코드의 로직 오류가 아니며, **부동소수점 Epsilon 정책 및 검증 로직이 의도대로 정밀하게 작동**했음을 입증합니다.

### (3) 성능 분석 및 시간 복잡도 $O(N^2)$ 증명

#### [크기별 평균 성능 측정 결과 표]

| 크기 ($N \times N$) | 평균 연산 시간 (ms) | 연산 횟수 ($N^2$) |
| --- | --- | --- |
| **5 x 5** | 0.0040ms | 25회 |
| **13 x 13** | 0.0311ms | 169회 |
| **25 x 25** | 0.1669ms | 625회 |

*(※ 각 크기별 2개 패턴의 평균 측정 시간을 합산 집계한 결과입니다.)*

#### [시간 복잡도 $O(N^2)$ 근거 서술]

* **원리 분석:** $N \times N$ 크기의 패턴 및 필터 데이터에서 MAC 연산을 수행하기 위해서는 2차원 배열의 모든 원소($N \times N$)를 1회씩 방문해야 하므로 총 연산 횟수는 정확히 $N^2$번 실행됩니다. 따라서 이론적 시간 복잡도는 $O(N^2)$입니다.
* **측정 결과와의 연관성:**
* $N=5$에서 $N=13$으로 증가 시, 연산 횟수는 $25 \to 169$로 약 **$6.76$배** 증가하였고, 실측 평균 연산 시간 또한 $0.0040\text{ms} \to 0.0311\text{ms}$로 약 **$7.77$배** 증가했습니다.
* $N=5$에서 $N=25$로 증가 시, 연산 횟수는 $25 \to 625$로 **$25$배** 늘어났고, 실측 평균 연산 시간 역시 $0.0040\text{ms} \to 0.1669\text{ms}$로 약 **$41.7$배** 증가하여 $O(N^2)$ 제곱 비례 관계를 입증하였습니다.

## 4. 트러블슈팅 및 깊이 있는 분석 (Troubleshooting)

### 이슈 1. `self.mode1_run()` 호출 시 `TypeError` 발생

* **원인:** `Mode_1` 클래스 인스턴스 뒤에 소괄호 `()`를 붙여 함수처럼 호출하려고 했으나, 클래스 내부에 `__call__` 메서드가 정의되어 있지 않아 발생함.
* **해결 방법:**
* **방법 A:** `Mode_1` 클래스의 메인 실행 함수명을 `__call__(self)`로 변경하여 인스턴스 직접 호출 가능하게 수정.
* **방법 B:** `self.mode1_run.mode1_flow()` 형태와 같이 명시적인 일반 메서드로 분리 호출하도록 수정.



### 이슈 2. `Matrix` 클래스 인스턴스 생성 시 `TypeError` 발생

* **원인:** 모드 1은 크기만 지정하는 방식(`Matrix(n_size)`), 모드 2는 크기와 데이터를 동시에 전달하는 방식(`Matrix(n_size, data)`)을 사용하여 매개변수 개수 불일치 발생.
* **해결 방법:** `Matrix` 클래스의 `__init__` 메서드 매개변수에 기본값(`data: list = None`)을 추가하여 1개 및 2개 인자 전달을 모두 유연하게 수용할 수 있도록 개선함.

```python
class Matrix:
    def __init__(self, size: int, data: list = None):
        self.size = size
        self.data = data if data is not None else []

```

### 이슈 3. MAC 연산 순서 및 부동소수점 오차로 인한 완전 동점 문제 상세 분석

#### A. 부동소수점(Floating Point)의 원리 및 연산 오차

파이썬의 `float` 타입은 IEEE 754 64비트(Double Precision, 가수부 52비트)를 따릅니다.
컴퓨터는 메모리를 [부호 1비트] + [지수부 11비트] + [가수부 52비트]로 나눕니다.

* **오차 발생 원인:** $0.1$ 등 10진수 실수를 2진수로 변환할 때 무한순환소수가 발생하며, 가수부(52비트) 한계를 초과하는 비트는 잘림(Truncation) 및 반올림(Rounding) 처리가 일어납니다.
* **결합법칙 미성립:** 부동소수점 연산은 더하는 순서에 따라 자릿수 맞추기 과정에서 누락되는 하위 비트(ULP) 위치가 달라지므로 **$(a + b) + c \neq a + (b + c)$** 특성을 가집니다.

#### B. 기존 방식 1(`sum` + Generator)이 완전 동점으로 실패했던 이유

```python
# 기존 방식 1
s1 = sum(self.data[r][c] * pathern.data[r][c] for r in range(n) for c in range(n))

```

* **문제 진단:** 파이썬 `sum()` C-구현체 내부에서 제너레이터를 소진하며 연산할 때, 데이터의 대칭적 특징과 결합하여 Cross 및 X 점수가 **소수점 아래 메모리 비트(가수부 52비트) 수준까지 $100\%$ 완벽히 동일한 $0.9, 7.5, 4.9$로 정밀 보정/절삭**되었습니다.
* **출력 자릿수 조절의 한계:** 이는 단순히 화면 표시상의 문제가 아니라 비트 단위에서 이미 동일한 실수로 저장된 것이므로, `print` 출력 자릿수를 늘려도 값이 다르게 나타나지 않습니다.
* **해결책:** 연산 순서를 변경(열 우선 순회)하거나 명시적 변수 누적 연산(이중 `for`문)을 적용하여, 누적 오차가 미세하게 갈리도록 구조를 변경해 판정을 성공시켰습니다.

## 5. 대규모 데이터($1000 \times 1000$) 확장성 및 성능 최적화

$1000 \times 1000$ 이상의 대규모 행렬 데이터 환경에서 연산을 수행할 경우, 단순 직렬 계산 알고리즘은 **메모리 대역폭 제한**과 캐시 미스(Cache Miss)로 인해 급격한 성능 저하가 발생합니다.

### 5.1. 예상 주요 병목 (Bottlenecks)

1. **L1/L2/L3 캐시 미스 폭증:**
$1000 \times 1000$ `float64` (Double) 행렬 하나의 크기는 약 **8 MB**입니다. 이는 일반적인 CPU의 L1/L2 캐시(초고속 임시 메모리) 용량(수백 KB ~ 수 MB)을 초과하므로 메인 메모리(DRAM) 접근이 폭증하여 메모리 대역폭 병목(흐름 정체, 속도저하)이 심화됩니다.
2. **불연속 메모리 접근 (Stride Access):**
열 우선(Column-major) 순회나 대각선 방향 순회 시 CPU 캐시 라인(64byte) 활용도가 떨어져 메모리 읽기 성능이 급격히 하락합니다.

### 5.2. 우선 최적화 방안 (Optimization Strategies)

* **메모리 레이아웃 연속성 확보 (C-Contiguous Alignment):**
배열 데이터를 메모리상에 연속적으로 배치하여 CPU의 하드웨어 프리패처가 다음 데이터를 효율적으로 미리 캐시하도록 구성합니다.

## 6. CPU(직렬) vs NPU(병렬) 병목 분석 및 오프로드(Offload) 전략

MAC(Multiply-Accumulate) 및 행렬 연산 시스템을 하드웨어 특성에 맞춰 최적화하기 위해 CPU와 NPU의 역할을 명확히 분담합니다.

```text
[ CPU ] ──(데이터 전송 병목 / Bus Latency)──> [ NPU Accel ]
 제어 로직 / 직렬 연산                          대규모 병렬 행렬 연산 (MAC)

```

### 6.1. 하드웨어 관점의 병목 비교

| 구분 | CPU (Central Processing Unit) | NPU (Neural Processing Unit) |
| --- | --- | --- |
| **특성** | **낮은 지연 시간(Latency), 강력한 직렬 분기 제어** | **높은 처리량(Throughput), 초대형 MAC 병렬 연산** |
| **적합한 연산** | 조건문, 예외 처리, 정규화, 단일 제어 로직 | 대규모 행렬 곱셈/누적, 컨볼루션(Conv2D) 연산 |
| **주요 병목** | 수백만 번 반복되는 루프의 대기 시간 | **Host-to-Device 데이터 전송 오버헤드 (PCIe/Bus)** |

### 6.2. NPU 오프로드 우선순위 가이드라인

1. **최우선 대상 (NPU Offload):**
* **$1000 \times 1000$ 수준의 대규모 MAC / 행렬 연산:**
NPU 내부의 **Systolic Array** 구조를 활용하여 수천 개의 곱셈-누적(MAC) 연산을 단일 클럭 사이클 단위로 동시 처리하므로 CPU 대비 상당한 성능 향상을 달성합니다.


2. **CPU 처리 권장 (Low Priority):**
* **소규모 데이터 연산 ($13 \times 13$, $25 \times 25$ 등):**
소규모 연산은 연산량 대비 Host-to-Device 데이터 전송 비용(Bus Latency)이 훨씬 크므로 CPU에서 직접 연산하는 것이 유리합니다.
* **결과 비교 및 판정 로직 (Post-Processing):**
Cross / X 점수의 크기를 비교하고 동점(`UNDECIDED`) 여부를 판단하는 조건 분기 로직은 CPU가 수행합니다.

## 7. 리팩토링 및 배운 점 
* **`process_pattern_flow` 메서드 구조화:** 단일 메서드로 집중되어 있던 JSON 파싱, $N$ 크기 추출, 데이터 검증 및 연산 과정을 `load_data` 및 검증 메서드로 세분화하여 코드 재사용성과 유지보수성을 극대화함.
* **불변 데이터와 튜플 (Tuple):** 실행 중 변경되지 않아야 하는 설정값과 고정 데이터 보호에 튜플 구조가 최적임을 익힘.
* **`dict.items()` 및 지연 평가:** 딕셔너리 순회 효율화와 제너레이터의 메모리 절약 원리를 깊이 이해하고 실전에 적용함.

```

```
