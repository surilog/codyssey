# 발행-구독 브로커 (Pub/Sub) 및 비동기 메시징 아키텍처 정리

본 문서는 필기 노트와 소스 코드 분석을 바탕으로, 전통적인 1:1 Key-Value 스토리지의 한계를 넘어 1:N 실시간 브로드캐스팅을 구현한 **Mini-Redis의 Pub/Sub 브로커 모듈(`pubsub.py`)**, **`HashMap`, `DoublyLinkedList`, `Queue` 3대 자료구조의 삼위일체 결합 설계**, **양방향 교차 매핑(`channels` vs `client_channels`)의 필요성**, **이중 연결 리스트 노드 래퍼(`curr`)와 실제 구독자 인스턴스(`curr.value`)의 구조적 차이**, **메모리 누수 방지를 위한 능동적 채널 정리(Clean-up)**, 그리고 **시간 복잡도와 기술 면접 Q&A**를 총정리한 학습 문서입니다.

---

## 1. 1:1 Key-Value 질의응답 vs 1:N 발행-구독 (Pub/Sub)

### 1) 패러다임의 차이
- **1:1 질의응답 (`GET` / `SET`)**: 
  - 클라이언트가 특정 키를 요청하면 서버가 해당 키에 매핑된 단일 값을 즉시 반환하는 동기식 1:1 대화 모델입니다.
- **1:N 브로드캐스팅 (`PUBLISH` / `SUBSCRIBE`)**: 
  - 다수의 청취자(Subscriber)가 특정 관심 주제인 **채널(Channel)**을 구독하고 대기합니다.
  - 발행자(Publisher)가 채널에 메시지를 한 번만 쏘아 올리면, 해당 채널에 접속 중인 **모든 청취자의 개인 우편함으로 메시지가 실시간 동시 전송**되는 비동기 다자간 방송 모델입니다.

---

## 2. 자료구조 삼위일체 설계 (Architecture)

Mini-Redis는 파이썬 내장 `dict`, `set`, `list`를 배제하고, 앞서 구현한 **3가지 순수 자료구조를 유기적으로 결합**하여 고성능 인메모리 메시지 브로커를 구축했습니다.

```text
[장부 1: self.channels (HashMap)] ──> 채널별 청취자 명단 관리
  "news"   ──> [DoublyLinkedList] ──> [Node: Subscriber("Alice")] <──> [Node: Subscriber("Bob")]
  "sports" ──> [DoublyLinkedList] ──> [Node: Subscriber("Alice")]

[장부 2: self.client_channels (HashMap)] ──> 클라이언트별 구독 채널 명단 관리 (역방향 장부)
  "Alice"  ──> [DoublyLinkedList] ──> [Node: "news"] <──> [Node: "sports"]
  "Bob"    ──> [DoublyLinkedList] ──> [Node: "news"]

[각 구독자의 개인 우편함 버퍼]
  Subscriber("Alice").message_queue ──> [Queue (FIFO)] ──> [ ("news", "속보 1"), ("news", "속보 2") ]
```

### 1) 3대 자료구조의 역할 분담 이유
| 사용 자료구조 | 역할 | 선정 이유 |
| :--- | :--- | :--- |
| **`HashMap`** | 채널 및 클라이언트 장부 | 채널명이나 클라이언트 ID를 Key로 삼아 구독자 목록 리스트를 **$O(1)$**에 즉시 탐색 |
| **`DoublyLinkedList`** | 채널별 구독자 목록 | 구독자 추가 시 Tail에 $O(1)$ 삽입, 구독 해제(`UNSUBSCRIBE`) 시 포인터 우회로 **$O(1)$ 노드 삭제** |
| **`Queue`** | 구독자 개인 메시지 우편함 | 발행자가 보낸 메시지가 누락되거나 뒤섞이지 않고 **도착한 순서대로 배달(FIFO)**되도록 보장 |

## 3. 왜 해시맵을 2개로 나누어 교차 관리하는가? (양방향 매핑)

Mini-Redis 브로커는 `self.channels`와 `self.client_channels`라는 2개의 독립된 해시맵을 동시에 유지합니다.

```text
┌─────────────────────────────────┐       ┌─────────────────────────────────┐
│     self.channels (정방향 장부)  │       │  self.client_channels (역방향 장부)│
│       채널 ──> 구독자 목록       │  <═>  │       클라이언트 ──> 채널 목록    │
└─────────────────────────────────┘       └─────────────────────────────────┘
```

1. **`self.channels` (채널 $\rightarrow$ 구독자 목록)**:
   - 메시지를 발행할 때(`PUBLISH news "속보"`), 채널 이름을 Key로 삼아 **"이 메시지를 받아야 할 청취자 리스트"**를 $O(1)$로 즉시 추출하기 위해 필요합니다.
2. **`self.client_channels` (클라이언트 $\rightarrow$ 채널 목록)**:
   - Redis 표준 프로토콜 규격상, `SUBSCRIBE` 및 `UNSUBSCRIBE` 명령의 반환값은 **"현재 이 클라이언트가 구독 중인 총 채널 수"**입니다.
   - 만약 역방향 장부가 없다면, 특정 클라이언트가 몇 개의 채널을 구독 중인지 계산하기 위해 모든 채널의 연결 리스트를 전수 순회($O(C \times K)$)해야 합니다.
   - 역방향 장부를 유지함으로써 **클라이언트의 현재 활성 구독 채널 수를 $O(1)$에 즉시 반환**할 수 있습니다.

## 4. 노드 래퍼(`curr`)와 실제 구독자 객체(`curr.value`)

가장 혼동하기 쉬운 핵심 개념입니다.

```python
subscriber: Subscriber = curr.value
subscriber.message_queue.enqueue((channel, message))
```

```text
       이중 연결 리스트 (기차)
      ┌────────────────────────────────────────────────────────┐
      │  [ Node (curr) ] ──prev / next──> [ Node ]             │
      │  ┌───────────────────────┐                             │
      │  │ key   : "client_1"    │ (포장 상자 / 래퍼)          │
      │  │ value : ─────────────┐│                             │
      └──┴──────────────────────│┴─────────────────────────────┘
                                │ (참조 포인터)
                                ▼
                   ┌─────────────────────────┐
                   │ Subscriber 인스턴스     │ (진짜 알맹이 내용물)
                   │  - client_id: "client_1"│
                   │  - message_queue: Queue │ ──> 개인 우편함
                   └─────────────────────────┘
```

- **`curr` (노드 래퍼 객체, `Node`)**:
  - `DoublyLinkedList`에서 앞뒤 노드를 잇는 연결 포인터(`prev`, `next`)를 담당하는 **택배 상자**입니다.
  - 노드 자체는 메시지 저장 큐(`message_queue`)를 가지고 있지 않습니다.
- **`curr.value` (실제 구독자 모델, `Subscriber`)**:
  - 택배 상자를 열었을 때 들어있는 **실제 구독자 인스턴스(알맹이)**입니다.
  - 여기에 개인 메시지 큐(`message_queue`)가 들어있으므로, 반드시 `curr.value`를 통해 알맹이 객체를 꺼낸 뒤 `enqueue()`를 호출해야 합니다.

## 5. 능동적 자원 회수 (Memory Clean-up)

구독 해제(`unsubscribe`) 시 메모리 누수를 방지하기 위한 핵심 로직입니다.

```python
# 구독자가 탈퇴하여 리스트의 크기가 0이 된 경우
if sub_list.size == 0:
    self.channels.remove(channel)  # 채널 장부에서 빈 껍데기 리스트 완전 제거!
```

- **문제 상황**: 사용자들이 채널을 구독했다가 모두 퇴장했을 때, 빈 `DoublyLinkedList` 껍데기 객체를 `self.channels` 해시맵에 그대로 남겨두면 어떻게 될까요?
- **결과**: 서비스가 장시간 운영되면서 수많은 일회성 채널이 생성·소멸할 때, **구독자가 0명인 유령 채널 노드들이 해시맵에 무한히 누적되어 심각한 메모리 누수(Memory Leak)**를 유발합니다.
- **해결**: 구독자 수가 0이 되는 즉시 해시맵에서 해당 채널 엔트리 자체를 영구 삭제하여 메모리를 즉각 회수합니다.

## 6. 자료구조 연산 시간 복잡도

| 연산 | 명령어 | 구현 자료구조 | 시간 복잡도 | 성능 분석 이유 |
| :--- | :--- | :--- | :---: | :--- |
| **채널 목록 조회** | 내부 탐색 | `HashMap` | **$O(1)$** | 채널 문자열 해싱을 통해 해당 연결 리스트 주소로 즉시 이동 |
| **구독자 추가** | `SUBSCRIBE` | `DoublyLinkedList` | **$O(1)$** | 리스트 끝단(Tail)에 노드 포인터만 재연결하여 삽입 |
| **구독자 삭제** | `UNSUBSCRIBE` | `DoublyLinkedList` | **$O(1)$** | 노드 참조 획득 후 앞뒤 포인터를 우회 연결하여 즉시 제거 |
| **메시지 푸시** | `PUBLISH` | `Queue` (FIFO) | **$O(1)$** | 구독자 개인 우편함 끝단에 $O(1)$로 메시지 삽입 (`enqueue`) |
| **전체 메시지 발행** | `PUBLISH` | 브로드캐스팅 루프 | **$O(S)$** | $S$ = 해당 채널을 구독 중인 실제 청취자 수만큼만 순회하여 전달 |
