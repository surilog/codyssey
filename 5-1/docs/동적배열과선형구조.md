# 동적 배열(DynamicArray) 및 선형 자료구조(Stack, Queue, Deque) 핵심 정리

본 문서는 **동적 배열(DynamicArray)**의 분할 상환 $O(1)$ 원리, **이중 연결 리스트(DoublyLinkedList)를 부품으로 재사용한 선형 자료구조 3형제(스택, 큐, 덱)**의 어댑터 패턴 구현, 그리고 **프로젝트 내 상위 모듈(Pub/Sub, 트리 BFS 순회, 해시 버킷, 힙)과의 유기적 결합 구조**를 총정리한 학습 문서입니다.

---

## 1. 동적 배열 (`dynamic_array.py`)

### 1) What? (개념 및 필요성)
- **개념**: 물리적으로 고정된 크기(Capacity)의 배열을 사용하되, 데이터가 가득 차면 **기존 용량의 2배(Geometric Doubling)**로 새 배열을 할당하여 기존 원소를 복사·이전시키는 가변 배열 자료구조입니다.
- **필요성**: 파이썬의 기본 `list`는 크기가 자유롭게 늘어나지만 내부적으로 C언어로 구현된 블랙박스입니다. 본 프로젝트에서는 내장 컬렉션 제약 조건을 준수하기 위해 밑바닥부터 2배 확장 메커니즘을 직접 구현했습니다.

---

### 2) Where? (프로젝트 내 핵심 연결 위치)
직접 구현한 `DynamicArray`는 프로젝트의 핵심 두 곳에서 파이썬 내장 리스트를 완벽히 대체하는 뼈대로 사용되었습니다.

```text
[DynamicArray의 핵심 사용처]
  ├── ① hash_map.py : self.buckets (0~15번 버킷 서랍장 배열)
  └── ② min_heap.py : self.heap    (완전 이진 트리 노드 배열)
```

1. **`hash_map.py`의 버킷 배열 (`self.buckets`)**:
   - 해시 함수가 계산한 방 번호(`index = hash(key) % capacity`)로 즉시 건너가야 합니다.
   - 인덱스를 통한 물리적 임의 접근(Random Access)이 반드시 **$O(1)$**이어야 하므로 동적 배열이 필수적입니다.
2. **`min_heap.py`의 완전 이진 트리 배열 (`self.heap`)**:
   - 최소 힙은 부모-자식 인덱스 계산 공식(`(i-1)//2`, `2i+1`, `2i+2`)으로 동작합니다.
   - 계산된 인덱스로 즉시 이동하여 노드를 비교하고 맞교환(`_swap`)해야 하므로 **$O(1)$ 접근**이 보장되는 동적 배열을 채택했습니다.

---

### 3) 분할 상환 시간 복잡도 (Amortized $O(1)$) 증명

새 공간을 할당받고 기존 $N$개의 원소를 복사할 때 일시적으로 $O(N)$의 비용이 발생합니다. 하지만 2배씩 늘려주면 이사하는 주기가 기하급수적으로 길어집니다.

```text
[용량 2배 확장 시 복사 비용의 누적]
크기 1에서 시작하여 N개 삽입 시 복사 횟수:
1 + 2 + 4 + 8 + ... + (N/2) = N - 1 < N
```

$$T(N) = \underbrace{N \text{ (순수 원소 삽입)}}_{O(N)} + \underbrace{(N - 1) \text{ (총 이사 복사 비용)}}_{O(N)} = 2N - 1$$

따라서 원소 1회 삽입당 평균 비용은 다음과 같습니다:

$$\text{Amortized Cost} = \frac{2N - 1}{N} \approx 2 \implies \mathbf{O(1)}$$

> **매번 1칸씩 늘렸다면?**  
> $1 + 2 + 3 + \dots + N = \frac{N(N+1)}{2} = O(N^2)$이 되어 원소 1개당 평균 $O(N)$의 치명적인 성능 저하가 발생합니다. 2배 확장이 $O(1)$을 만드는 핵심 열쇠입니다.

---

### 4) 매직 메서드(Magic Methods)를 통한 내장 시퀀스 호환

외부 모듈(`HashMap`, `MinHeap`)에서 파이썬 내장 리스트 문법을 그대로 사용할 수 있도록 4대 매직 메서드를 구현했습니다.

```python
def __len__(self) -> int:
    return self.size  # len(arr) 호출 시 실제 저장된 유효 데이터 개수 반환

def __getitem__(self, index: int):
    return self.get(index)  # arr[i] 조회 지원 (O(1))

def __setitem__(self, index: int, value):
    self.set(index, value)  # arr[i] = val 수정 지원 (O(1))

def __iter__(self):
    for i in range(self.size):
        yield self._array[i]  # for x in arr 순회 지원 (빈 방 None 제외)
```

## 2. 선형 자료구조 3형제 (`linear_structures.py`)

### 1) What? (입·출력 원칙 한눈에 비교)

| 자료구조 | 입·출력 원칙 | 동작 방식 | 비유 | 주요 특징 |
| :--- | :---: | :--- | :--- | :--- |
| **스택 (Stack)** | **LIFO** (Last-In First-Out) | 한쪽 끝(Top)에서만 넣고 뺌 | 프링글스 감자칩 통, 책 쌓기 | 가장 최근에 들어간 데이터가 먼저 나옴 |
| **큐 (Queue)** | **FIFO** (First-In First-Out) | 뒤(Tail)로 넣고 앞(Head)으로 뺌 | 은행 대기표, 맛집 줄서기 | 가장 먼저 들어간 데이터가 먼저 나옴 |
| **덱 (Deque)** | **양방향 자유** | 앞/뒤 양쪽 끝 모두에서 넣고 뺌 | 양쪽이 뚫린 터널 | 스택과 큐를 완벽하게 포괄하는 만능형 |

---

### 2) How? (이중 연결 리스트를 감싼 어댑터 패턴)

일반 배열로 큐나 덱을 만들면 앞에서 꺼낼 때(`pop(0)`) 빈자리를 채우기 위해 뒤 요소를 한 칸씩 앞으로 당겨오는(Shift) **$O(N)$의 지연**이 발생합니다.  
따라서 이미 검증된 `DoublyLinkedList`를 내부 부품으로 품고 겉모습만 바꾸는 **어댑터(Adapter) / 컴포지션(Composition) 패턴**을 적용했습니다.

```text
[Adapter Pattern 구조]
  Stack / Queue / Deque  (외부 인터페이스: push, pop, enqueue, dequeue)
           │
           ▼ 호출 위임
   DoublyLinkedList      (내부 실제 구현: insert_front, remove_front, insert_back 등)
```

---

### 3) 필기 노트 속 연결 리스트 매핑 메서드 비교표 (100% 반영)

`DoublyLinkedList`는 `Node(key, value)` 구조이므로, 단일 데이터(`item`)를 다룰 때는 `key=item`, `value=None` 형태로 삽입하고 꺼낼 때 `node.key`를 반환합니다.

| 자료구조 | 연산 인터페이스 | 연결 리스트 호출 메서드 | 내부 동작 설명 | 시간 복잡도 |
| :--- | :--- | :--- | :--- | :---: |
| **Stack** | `push(item)` | `insert_front(item, None)` | 맨 앞(Top)에 노드 추가 | **$O(1)$** |
| | `pop()` | `remove_front()` | 맨 앞 노드 제거 후 `node.key` 반환 | **$O(1)$** |
| | `peek()` | `dummy_head.next.key` | 맨 앞 노드 데이터만 확인 | **$O(1)$** |
| **Queue** | `enqueue(item)` | `insert_back(item, None)` | 맨 뒤(Tail)에 줄 세우기 | **$O(1)$** |
| | `dequeue()` | `remove_front()` | 맨 앞(Head)부터 꺼내어 퇴장 | **$O(1)$** |
| | `peek()` | `dummy_head.next.key` | 맨 앞 대기자 데이터 확인 | **$O(1)$** |
| **Deque** | `append_front(item)`| `insert_front(item, None)` | 맨 앞에 원소 삽입 | **$O(1)$** |
| | `append_back(item)` | `insert_back(item, None)` | 맨 뒤에 원소 삽입 | **$O(1)$** |
| | `pop_front()` | `remove_front()` | 맨 앞 원소 꺼내기 | **$O(1)$** |
| | `pop_back()` | `remove_back()` | 맨 뒤 원소 꺼내기 | **$O(1)$** |

---

### 4) 프로젝트 내 자료구조 재활용 연계 (Where?)

여기서 구현된 **`Queue`**는 상위 계층의 핵심 기능 2곳에 직결되어 재활용됩니다.

```text
                               ┌─────────────────────────┐
                               │   Queue (선입선출 큐)    │
                               └─────────────────────────┘
                                     /             \
                                    /               \
                                   ▼                 ▼
             [1. pubsub.py 메시지 브로커]    [2. binary_tree.py 레벨 순회]
             - Subscriber.message_queue      - levelorder(root) (BFS)
             - 발행 순서대로 수신자에게 배달     - 아파트 1층부터 층별 방문 대기열
```

1. **`pubsub.py` (발행-구독 메시지 버퍼)**:
   - 각 구독자 객체(`Subscriber`)마다 개인 우편함으로 `self.message_queue = Queue()`를 소유합니다.
   - 발행자(`Publisher`)가 보낸 메시지가 섞이지 않고 **발행된 순서 그대로(FIFO)** 구독자에게 배달됩니다.
2. **`binary_tree.py` (너비 우선 탐색 BFS 레벨 순회)**:
   - 트리의 계층별 방문(`levelorder`)을 구현할 때 루트부터 자식 노드들을 큐에 `enqueue`하고, 앞에서 `dequeue`하며 방문하는 **BFS 대기열**로 사용됩니다.

## 3. 동적 배열 vs 이중 연결 리스트 비교 및 역할 분담

### 1) 4대 기본 연산 시간 복잡도 비교

| 연산 구분 | 동적 배열 (`DynamicArray`) | 이중 연결 리스트 (`DoublyLinkedList`) |
| :--- | :---: | :---: |
| **임의 인덱스 접근 (`arr[i]`)** | **$O(1)$** (주소 산술 연산으로 즉시 점프) | $O(N)$ (Head부터 링크 타고 순차 이동) |
| **임의 값 탐색 (`Search`)** | $O(N)$ (처음부터 선형 순회) | $O(N)$ (처음부터 링크 순회) |
| **노드 주소를 알 때 삽입/삭제** | $O(N)$ (뒤쪽 원소 Shift 필요) | **$O(1)$** (앞뒤 포인터 링크만 재연결) |
| **맨 앞 삽입 / 삭제** | $O(N)$ (전체 데이터를 밀고 당김) | **$O(1)$** (더미 헤드 바로 뒤 조작) |
| **맨 뒤 삽입 (`append`)** | **분할 상환 $O(1)$** | **$O(1)$** (더미 테일 바로 앞 조작) |
| **메모리 연속성 및 캐시 효율** | **매우 높음** (연속 공간 $\rightarrow$ 지역성 우수) | 낮음 (노드가 메모리 곳곳에 분산 할당) |

---

### 2) 왜 둘을 섞어 썼는가? (철저한 역할 분담의 당위성)

두 자료구조의 강점과 약점이 완벽히 반대이므로, Mini-Redis 엔진은 요구사항에 맞춰 칼같이 역할을 분리했습니다.

```text
┌──────────────────────────────────────┬──────────────────────────────────────┐
│       DynamicArray 채택 영역         │      DoublyLinkedList 채택 영역      │
├──────────────────────────────────────┼──────────────────────────────────────┤
│ • hash_map.py 버킷 서랍장            │ • LRU 캐시 순서 관리 (move_to_front) │
│   (해시 숫자로 O(1) 즉각 점프 필요)  │   (O(1) 빈번한 중간 노드 추출/이동)  │
│                                      │                                      │
│ • min_heap.py 완전 이진 트리 배열    │ • LinearStructures (스택, 큐, 덱)    │
│   (부모/자식 인덱스 수학 계산 점프)  │   (맨 앞 데이터 꺼내기 Shift O(N) 방어│
│                                      │                                      │
│                                      │ • pubsub.py 구독자 대기열            │
└──────────────────────────────────────┴──────────────────────────────────────┘
```

- **조회(탐색) 기준의 차이**:
  - **동적 배열의 $O(1)$**: 숫자 인덱스(순번)를 알고 있을 때 즉시 순간이동.
  - **해시맵의 $O(1)$**: 문자열 Key를 해시 함수로 변환하여 동적 배열의 인덱스로 접근.
  - **이중 연결 리스트의 $O(1)$**: 이미 주소를 확보한 노드를 앞뒤에서 떼어내고 붙일 때.
- **결론**: 숫자 번지수 점프가 필수인 **버킷과 힙**에는 동적 배열을, 포인터 조작을 통한 순서 갱신과 양 끝단 삭제가 잦은 **LRU 캐시와 큐**에는 이중 연결 리스트를 결합하여 전체 시스템 복잡도를 $O(1)$로 완성했습니다.
