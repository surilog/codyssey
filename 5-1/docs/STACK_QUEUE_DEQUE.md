# 스택(Stack), 큐(Queue), 덱(Deque) 구조 및 활용 보고서 
 **문서명**: `STACK_QUEUE_DEQUE.md`  
 **프로젝트**: Mini Redis 기반 선형 자료구조 분석 및 실전 활용 
 --- 
 ## 1. 개요 및 학습 목적 
 
 Mini Redis 프로젝트에서 구현한 **이중 연결 리스트(`DoublyLinkedList`)**와 **동적 배열(`DynamicArray`)**은 다양한 선형 자료구조의 핵심 기반이 됩니다. 
 
 본 문서는 컴퓨터 과학의 대표적인 선형 자료구조인 **스택(Stack)**, **큐(Queue)**, **덱(Deque)**의 내부 원리와 동작 규칙, 시간 복잡도를 체계적으로 정리하고, 향후 **Pub/Sub(발행-구독) 메시징 버퍼** 및 **CLI 커맨드 히스토리** 기능의 밑바탕이 되는 자료구조적 설계 원리를 확립하는 것을 목적으로 합니다. 

 --- 
 
 ## 2. 자료구조별 상세 분석 
 ### 2.1 스택 (Stack) 
 * **기본 원칙**: **LIFO (Last In First Out, 후입선출)** 가장 마지막에 삽입된 데이터가 가장 먼저 제거되는 구조입니다. 
 * **주요 연산**: * `push(item)`: 스택 맨 위에 새로운 원소를 추가합니다. 
    * `pop()`: 스택 맨 위의 원소를 꺼내어 제거하고 반환합니다. 
    * `peek()` / `top()`: 스택 맨 위의 원소를 제거하지 않고 조회합니다. 
    * `is_empty()`: 스택이 비어있는지 확인합니다. 
 * **대표 활용 사례**: 
 * 함수 호출 스택 (Call Stack / 재귀 함수 관리) 
 * 실행 취소 및 다시 실행 (Undo / Redo, Ctrl+Z) 
 * 수식 괄호 유효성 검사 및 후위 표기법(Postfix) 연산 
 --- 
 ### 2.2 큐 (Queue) 
 * **기본 원칙**: **FIFO (First In First Out, 선입선출)** 가장 먼저 삽입된 데이터가 가장 먼저 제거되는 구조입니다. 
 * **주요 연산**: 
 * `enqueue(item)`: 큐의 맨 뒤(Rear/Tail)에 원소를 추가합니다. 
 * `dequeue()`: 큐의 맨 앞(Front/Head) 원소를 꺼내어 제거하고 반환합니다. 
 * `peek()` / `front()`: 큐의 맨 앞 원소를 제거하지 않고 조회합니다. 
 * `is_empty()`: 큐가 비어있는지 확인합니다. 
 * **대표 활용 사례**: 
 * 운영체제(OS) 프로세스/스레드 CPU 스케줄링 대기열 * 네트워크 패킷 버퍼 및 프린터 인쇄 대기열 
 * **Redis Pub/Sub 구독자별 메시지 전송 버퍼 (Message Queue)** 
 --- 
 ### 2.3 덱 (Deque, Double-Ended Queue) 
 * **기본 원칙**: **양방향 자유 입출력** 양쪽 끝(Front, Rear) 모두에서 데이터의 삽입과 삭제가 자유롭게 일어나는 구조입니다. 
 * **주요 연산**: * `append_front(item)`: 덱의 맨 앞에 원소를 삽입합니다. 
 * `append_back(item)`: 덱의 맨 뒤에 원소를 삽입합니다. 
 * `pop_front()`: 덱의 맨 앞 원소를 꺼내어 삭제 및 반환합니다. 
 * `pop_back()`: 덱의 맨 뒤 원소를 꺼내어 삭제 및 반환합니다. 
 * `peek_front()` / `peek_back()`: 양 끝단 원소를 조회합니다. 
 * **대표 활용 사례**: 
 * 스택과 큐의 역할을 모두 대체할 수 있는 만능 자료구조 
 * 슬라이딩 윈도우(Sliding Window) 알고리즘 
 * 캐시 버퍼 및 작업 훔치기(Work Stealing) 스케줄러 
 --- 
 ## 3. 구현 방식 비교: 
 동적 배열 vs 이중 연결 리스트 스택, 큐, 덱은 내부 저장소를 **동적 배열(`DynamicArray`)**로 구현하느냐, **이중 연결 리스트(`DoublyLinkedList`)**로 구현하느냐에 따라 성능 특성이 명확하게 갈립니다. 
 
 | 자료구조 | 연산 | 동적 배열 (DynamicArray) | 이중 연결 리스트 (DoublyLinkedList) | 비고 |
| --- | --- | --- | --- | --- |
| **Stack** | `push` | O(1) (분할 상쇄) | O(1) | 둘 다 O(1)로 매우 우수함 |
|  | `pop` | O(1) | O(1) | 연속 메모리(캐시 지역성) 덕분에 배열이 소폭 유리 |
| **Queue** | `enqueue` | O(1) (분할 상쇄) | O(1) | 뒤쪽 삽입은 둘 다 빠름 |
|  | `dequeue` | **O(N)** (원소 이동 Shift 비용) | **O(1)** | **연결 리스트 압승** (단, 원형 큐 방식은 배열도 O(1)) |
| **Deque** | 양 끝단 삽입 | Front: O(N) / Back: O(1) | **Front/Back 모두 O(1)** | **더미 노드 기반 연결 리스트 최적** |
|  | 양 끝단 삭제 | Front: O(N) / Back: O(1) | **Front/Back 모두 O(1)** | 배열 앞단 조작 시 O(N) 데이터 이동 발생 |

 ### 3.1 동적 배열(`DynamicArray`) 구현의 특징 
 * **장점**: 메모리가 연속적으로 배치되어 **CPU 캐시 적중률(Cache Locality)**이 매우 높고 임의 접근(Random Access)이 O(1)로 빠릅니다. 
 * **한계**: 맨 앞의 원소를 제거(`dequeue` / `pop_front`)할 때 뒤쪽의 모든 원소를 한 칸씩 앞으로 당겨야(Shift) 하므로 **O(N)의 시간 복잡도**가 소요됩니다. (이를 극복하기 위해 인덱스를 회전시키는 '원형 큐' 기법을 사용합니다.) 
 
 ### 3.2 이중 연결 리스트(`DoublyLinkedList`) 구현의 특징 
 * **장점**: 양 끝에 **더미 헤드(`dummy_head`)와 더미 테일(`dummy_tail`)** 노드를 배치함으로써, 앞/뒤 양방향의 모든 삽입(`insert_front`, `insert_back`)과 삭제(`remove_front`, `remove_back`)가 예외 분기문 없이 **항상 O(1) 시간**에 처리됩니다. 
 * **한계**: 노드마다 데이터 외에 `prev`, `next` 포인터를 보관해야 하므로 메모리 오버헤드가 발생합니다.

 ## 4. Mini Redis 및 실제 Redis에서의 실전 활용 
 1. **Redis Pub/Sub (발행-구독) 메시징 큐**: 
    * 채널(Channel)에 메시지가 발행(`PUBLISH`)되면, 해당 채널을 구독(`SUBSCRIBE`)하고 있는 여러 클라이언트의 전송 버퍼에 메시지가 순서대로(FIFO) 쌓여야 합니다. 

    * 이때 이미 구현된 `DoublyLinkedList`를 큐 형태로 활용하면, O(1)의 속도로 메시지를 대기열에 적재하고 순차 전송할 수 있습니다. 
 2. **CLI 커맨드 히스토리 (Command History)**: 
    * 사용자가 입력한 최근 명령어들을 고정 크기의 덱(Deque) 또는 큐로 보관하여 위/아래 방향키 탐색이나 이전 명령 재실행을 지원할 수 있습니다. 
 3. **Redis List 타입과의 완벽한 일치 (`LPUSH`, `LPOP`, `LRANGE`)**: 
    * 실제 Redis의 `List` 자료구조는 내부적으로 양방향 연결 리스트(Quicklist) 기반으로 동작하여 사실상 **덱(Deque)**과 동일하게 동작합니다. 
 --- 
 ## 5. 결론 및 요약
  * **스택**은 후입선출(LIFO), **큐**는 선입선출(FIFO), **덱**은 양방향 입출력 구조입니다. 
  
  * 큐와 덱처럼 양 끝단에서 빈번한 삽입과 삭제가 일어나는 환경에서는, 배열의 앞단 원소 이동(O(N) Shift) 단점을 극복하는 **더미 노드 기반 이중 연결 리스트(`DoublyLinkedList`)가 가장 최적의 구현 방식**입니다. 
  
  * 본 문서에서 확립된 구조는 이후 Mini Redis의 Pub/Sub 및 비동기 작업 버퍼 구현의 탄탄한 토대가 됩니다.
